# Café print bridge (Task 24)

Before enabling unattended printing on a physical device, complete the [printer acceptance checklist](printing-resilience.md#manual-acceptance-checklist-for-the-actual-café-printer). The automated resilience suite uses the file simulator; it cannot prove paper emerged from a real printer.

The bridge is a separate Node process on the café computer. It connects outbound to the realtime service; Next.js never bundles it. Install the pinned Node/npm versions from `.nvmrc` and `package.json`, run `npm ci`, then install a local rendering browser with `npx playwright install chromium`. On Windows, an installed Chrome can be selected with `BRIDGE_BROWSER_CHANNEL=chrome` instead. Copy `.env.bridge.example` to `.env.bridge.local`, set its own 32+ character token and printer ID to match the **encrypted printing settings**, and keep the file readable only by the bridge service account. Never place the token in a URL, browser, logs, or Git. `npm run bridge:doctor` validates local configuration without printing. Start `npm run realtime:work` on the server, then `npm run bridge:run` on the café computer. A remote bridge must use `wss://` via the TLS reverse proxy; plain `ws://` is accepted only for loopback development.

Start with `BRIDGE_ADAPTER=file`. Automatic printing must be enabled in owner printing settings when the invoice is created. A paid order's `invoice.issued` outbox event creates one PrintJob, the server sends it when the bridge registers, Chromium shapes the self-contained Persian HTML with its embedded font, and the file adapter writes `data/print-bridge/simulated/{jobId}.escpos`. The first bytes should be `1B 40 1D 76 30 00`, followed by the raster and cut command. `npm run bridge:status` shows local journal counts and job IDs; the admin order print-status API shows the authoritative server state. The ignored `data/print-bridge/journal` is **operational state**, not a disposable cache: back it up, retain it while invoices may be replayed, and never wipe it to fix a printer problem.

For a TCP ESC/POS printer, set `BRIDGE_ADAPTER=network`, `BRIDGE_NETWORK_HOST` and `BRIDGE_NETWORK_PORT` (usually 9100, but confirm the model). Restrict this port to the café LAN. For a Windows USB printer, install and test its Windows driver, set `BRIDGE_ADAPTER=windows-spool` and the exact `BRIDGE_WINDOWS_PRINTER` name. The bridge calls the Windows RAW spooler with ESC/POS bytes via `bridge/winspool.ps1`. Test paper width, encoding-independent raster, cutter, and driver RAW support on the actual printer before unattended service. Some drivers transform RAW jobs or ignore cut commands; choose a compatible driver/printer. File mode is the safe default. Only one bridge may own a printer ID at a time, and the local journal lock blocks a second process using the same directory. A stale lock is reclaimed on restart only when its recorded process ID is no longer running; if the ID has been reused or the lock is corrupt, stop and inspect the process and lock rather than deleting it blindly.

The bridge journals `received` **before** touching the adapter, then `printed` after the adapter accepts bytes, then sends the exact version-1 ACK. The server alone marks the job printed after a matching ACK. If the ACK is lost, redelivery of that job ID is ACKed without another adapter call, including after restart. Definite pre-output failures are journaled as `failed` and error-ACKed; the server retries with a new attempt, up to its dead-letter limit. Ambiguous network/spool failures remain `received` for operator review. Reconnect uses capped exponential backoff and protocol heartbeats. Raw receipts, bridge tokens, customer data and HTML are not written to logs. File simulator receipts contain customer data; guard that directory accordingly.

There is an unavoidable crash window between a physical printer accepting bytes and the bridge persisting `printed`. A surviving `received` entry is therefore **held for operator review**, not automatically reprinted. Inspect the printer/spooler and paper. With the bridge stopped, run `npm run bridge:resolve -- JOB_ID printed --confirm` if it was printed, or `npm run bridge:resolve -- JOB_ID retry --confirm` only if it was not; then restart the bridge. The next server delivery sends the appropriate ACK or retries. If the server job already reached `dead`, an owner/cashier must request a new audited invoice reprint using the invoice reprint endpoint; this creates a new job ID for the same invoice. Do not edit or delete journal files to force a copy. The network and Windows adapters can confirm transport/spool acceptance, **not paper emergence**; physical exactly-once printing requires printer-specific status hardware/protocol and is not claimed here.

Diagnostics: `npm run bridge:doctor`, `npm run bridge:status`, `GET /ready` on the realtime process, and the admin order print-status API. `PAPER_OUT`/`PRINTER_*` errors require checking paper, USB/LAN, Windows queue, driver RAW support and spooler service. If registration fails, compare bridge ID/token with encrypted settings, check TLS proxy WebSocket upgrade, and ensure no second bridge owns that printer. If a job stays queued, verify MongoDB/Redis readiness and the realtime worker. Do not run Redis restart smoke checks while real jobs are flowing. Keep the service account and journal/data directory on a persistent local disk; for unattended Windows use an operator-managed service/task with automatic restart and a restricted account, after manual simulator and printer tests.
