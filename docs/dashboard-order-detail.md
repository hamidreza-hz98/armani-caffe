# Order detail operations

`/dashboard/orders/[id]` is an authenticated, noindex Server Component entrypoint. It reads the order through the orders application service, then loads the immutable invoice, payment state, bounded stock movements, audit trail and print jobs. The browser receives explicit DTOs, never Mongoose documents. The page works at desktop and mobile widths; the fulfillment timeline and next valid step remain prominent. The list links directly to the detail page.

Status advancement uses the existing version-checked order transition service. Only OWNER can cancel a `NEW` or `PREPARING` order, with a required reason. A refund action is exposed only for a cancelled, paid order without an existing request; it **requests** a refund and does not claim the money was returned. The owner-only transaction check validates the amount of an already settled, previously verified record; for an unsettled record it sends the stored transaction ID to the configured provider adapter for inquiry. Browser input cannot set payment success. These server-side checks remain mandatory even if UI controls are hidden.

The invoice preview reads the issued snapshot, including the saved business identity and Jalali display timestamp. Reprint requires explicit confirmation and a fresh idempotency key, then uses the existing audited invoice reprint service. If the browser loses the response, its session-scoped key is reused on retry so one user intention cannot create duplicate print attempts. A successful request clears the key, allowing a deliberate later reprint. Reprint adds a linked print attempt without changing or regenerating the invoice. Print jobs show queued, printing, printed, retrying (queued after an attempt) and failed/dead states. The authenticated print socket supplies bridge presence and job hints; the page re-fetches authoritative server data on every hint, reconnect, tab return and a 15-second interval. A socket outage yields unknown bridge presence, not an invented print failure; a failed server refresh marks the view stale and blocks status changes.

Run `npm run test:e2e:order-detail` for the production-like browser flow. The printing integration suite exercises the actual outbox → durable job → file-simulator bridge → ACK path and bridge presence transitions. The browser test verifies snapshot display, stock/activity, print-state reconciliation, guarded reprint, audit persistence, and status transition. Both suites use isolated test data; the simulator never touches a physical printer.
