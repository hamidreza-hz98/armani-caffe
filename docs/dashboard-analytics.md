# Dashboard analytics

`GET /api/admin/analytics/dashboard` is an owner-only, private/no-store read model. The service checks the server-side `analytics.read` capability before issuing queries. It returns no Mongoose documents, phone numbers, payment references, customer credentials, internal stock movements, or unbounded lists. All ranking and latest/stock lists are capped at ten. The query uses immutable order line/customer snapshots, so later catalog/profile edits do not rewrite historical sales.

“Today” means the current Gregorian calendar day in `Asia/Tehran`, from local midnight through the request instant. “30 days” means today plus the preceding 29 local calendar days, not a rolling 720-hour interval. The local boundaries are converted to UTC instants for indexed BSON `placedAt` comparisons. The response includes the Tehran date, UTC as-of instant, sales in integer تومان, count, and average order value rounded to the nearest تومان. A zero-order window has zero average. The clock is captured once per response, and all queries use a fixed upper bound to avoid future-dated records.

Gross paid sales/counts and rankings include only `paymentStatus=paid`, positive total, and status `NEW`, `PREPARING`, `READY`, or `COMPLETED`. Pending/unpaid/failed attempts, checkout recovery intents, cancelled orders, and refunded orders do not contribute. A paid order with a refund merely **requested** remains excluded if cancelled; it is not counted as net revenue. These are order sales, not cash-settlement/accounting metrics. Latest orders is an operational feed: it includes both paid and refunded confirmed orders, including cancellations, but excludes unconfirmed attempts. Customers rank by 30-day paid amount, then order count; customerless partial records still count in totals but not customer ranking. Products rank by 30-day paid quantity, then line sales. Current low stock includes active items with `onHand <= reorderLevel`, including zero. Names are snapshot names for orders and current names for stock.

The five MongoDB pipelines have `maxTimeMS=2500`, `allowDiskUse=false`, explicit index hints and final `$limit:10` stages for lists. The existing `order_payment_placed` index drives date scans, `order_recent` drives latest orders, and `inventory_low_stock_dashboard` drives stock status/on-hand order. The stock field-to-field threshold expression still needs a bounded active-item scan; it cannot use a simple scalar index bound on `reorderLevel`. Integration tests run `explain("queryPlanner")` against these named indexes. Apply the new index intentionally with `npm run db:indexes:plan` followed by `npm run db:indexes:apply -- --apply`; normal requests never build indexes. Review `executionStats` and production query latency after representative data is loaded.

This direct read model is appropriate while recent paid orders and active inventory fit comfortably within the query time budget. If dashboards approach timeout or date-window scans become large, add a versioned daily rollup keyed by Tehran local date, with integer sales/count and idempotent order/refund contribution keys. Build it from committed order/payment outbox events, reconcile it periodically against source orders, backfill historical days with an explicit command, and atomically swap the dashboard reader only after parity checks. Keep latest orders and low stock sourced from their live indexed collections. Do not update a rollup from browser callbacks or use it as the financial source of truth.
