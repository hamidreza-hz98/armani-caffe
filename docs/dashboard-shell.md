# Dashboard shell (Task 33)

`/dashboard/login` uses the existing admin authentication endpoint and accepts only an exact, known dashboard destination in `next`. It never redirects to a caller-supplied URL. `/dashboard` and its sections resolve the admin session on the server; the proxy's cookie-shape check is only an early guest redirect and is not an authorization decision. Every page check uses the capability map, and direct visits to owner-only sections display the custom 403 page without owner data. Since App Router can start streaming before the capability check resolves, this document response may have HTTP 200 even while displaying the denied state; protected APIs and services enforce their own authorization. All dashboard pages declare static `noindex`, `nofollow`, and `nocache` metadata. Legacy `/admin` routes remain available for compatibility.

The desktop shell has a permanent right sidebar. Below 900px it becomes a temporary RTL drawer. Breadcrumbs, order-code search, empty notification indicator, profile, and logout are interactive islands. Navigation is filtered from the shared OWNER/CASHIER capability map. The search accepts an exact `AC-` order code and performs one indexed, projected, timeout-bounded server query after authorization. Section content beyond the shell remains deliberately minimal until each dashboard feature task is implemented; notification delivery is not implied by the empty indicator.

On authentication expiry, a request redirects to `/dashboard/login?next=<known-section>`. The login page validates `next` again and returns to it after a successful login. Loading, retryable error, and 403 states are separate. Login and logout never persist credentials in browser storage.

Run `npm run test:e2e -- dashboard-shell.spec.ts` for guest/login layout checks. Run `npm run test:e2e:dashboard` for real OWNER/CASHIER navigation against a temporary, isolated MongoDB replica set. The second command creates a test-only owner and cashier and removes the temporary database when finished. It does not use development MongoDB. Both commands run a production build and a headless browser.
