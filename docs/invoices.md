# Immutable invoices and receipts

Migration 12 enables invoice snapshot v2. Apply it intentionally with `npm run db:migrate:up` and apply the new `invoice_reprints` indexes with `npm run db:indexes:apply` before taking payments. Requests never migrate or create indexes. Historical v1 invoices are untouched and require a deliberate reconciliation process; current settings must not be used to invent missing historical identity.

When verified payment confirms an order, the order repository inserts an invoice in the **same MongoDB transaction** as the order, inventory movements, cart closure, sales projection, audit event, and outbox events. A unique order ID and invoice number enforce one snapshot. Repeated confirmation returns the existing order; repeated `order.confirmed` handling reads the same invoice. An error at any stage rolls back the entire confirmation. The invoice stores the confirmed item/addition/customer/pricing/transaction snapshots, business/contact/footer settings, UTC issuance time, and a frozen Jalali Tehran display timestamp. Later catalog and settings edits do not change it. The new invoice has no update/void endpoint.

Authorized owner and cashier reads use `GET /api/admin/orders/{orderId}/invoice`; the owning customer uses `GET /api/customer/orders/{orderId}/invoice`. Add `/print` to get a self-contained, browser/PDF-friendly HTML receipt. The local Vazirmatn WOFF2 is embedded in the HTML response; no external font request is needed. HTML is escaped, uses `lang="fa" dir="rtl"`, and isolates Latin codes/phone/reference with `<bdi dir="ltr">`. The page defaults to the captured 58/80mm width; browser Print can save it as PDF.

Explicit reprint: `POST /api/admin/orders/{orderId}/invoice/reprint` with same-origin `Origin` and JSON `{"idempotencyKey":"unique-key-123","paperWidthMm":58}` (`paperWidthMm` optional). Each accepted key creates one `invoice_reprints` record and transactional `invoice.reprint_requested` audit/outbox entries; repeating the key returns the same receipt. This does **not** create a second invoice; the separate realtime printing process consumes its outbox event and queues a new PrintJob linked to the original invoice.

Thermal strategy: render the HTML with the embedded Persian font in a trusted browser/print bridge, rasterize at exactly 384 dots (58mm) or 576 dots (80mm), then pass PNG to `receiptPngToEscPos` for compact monochrome GS v 0 ESC/POS bytes and a cut command. Never send raw Persian text to a printer code page: Arabic joining and bidi support vary across firmware. Keep the raster height at most 8192 dots and preview on the target model before enabling unattended printing. The sample unit and Chromium tests cover Persian words, mixed references, long names, additions, both widths, local font loading, and horizontal overflow.
