# Application transport contracts

This is the human-readable inventory for the current App Router routes and realtime/bridge consumers. All `/api` JSON results except health and the media-file/invoice-HTML downloads use `{ ok: true, value: DTO }` or `{ ok: false, error: { code, message, requestId } }`. `error.message` is safe Persian text; internal exceptions, Mongoose documents, credentials, hashes, and stack traces are not transport contracts. Typical error codes are `VALIDATION` (400), `UNAUTHORIZED` (401), `FORBIDDEN` (403), `NOT_FOUND` (404), `CONFLICT` (409), `RATE_LIMITED` (429), and `UNAVAILABLE` (503). API responses carry `X-Request-ID`, `Cache-Control: no-store` (private where indicated), and `X-Content-Type-Options: nosniff`; clients may send a bounded `X-Request-ID` for correlation. All write bodies below are size-limited JSON unless specified otherwise, and browser cookie mutations require an approved same-origin `Origin`. A service must still enforce capability and ownership inside its application/repository layer; an HTTP route guard alone is not authority.

`{id}` is a 24-character MongoDB ID. Admin and customer HTTP-only cookies are separate. `OWNER` and `CASHIER` are the only admin roles. Cashier may read orders, inventory, catalog, public media and printing; only owner may read analytics or mutate admins, settings, catalog, products and media. Customers may only read/mutate their own profile, cart, checkout, orders and invoices. Public menu/category/media reads expose safe projections. Payment callbacks authenticate through provider-specific state and authoritative verification, not browser cookies or callback hints. A bridge uses its registered printer ID/token on the realtime socket, never an admin cookie.

No public arbitrary `POST` payment callback route is currently exported. The generic callback handler can parse bounded form POST for a future documented adapter, but the current route exposes only GET. No client can submit a print-success HTTP command; only the authenticated bridge socket can ACK the current leased job.

## Idempotency, concurrency, rate limits and external clients

`Idempotency-Key` is a required request header for settings and the applicable media mutations above. Checkout, inventory approval requests and invoice reprints currently carry a validated `idempotencyKey` **body field**; the domain stores it for retry safety. Other state mutations use an expected `revision`/atomic transition or independently idempotent business identity, not a universal HTTP replay key. Clients must reuse the same key for retries and generate a new key for a new operation. A `409` means reload current state before choosing a new revision; never blind-retry with invented prices/status. Login/signup use persistent per-identity throttles (429, `Retry-After: 900`); payment callbacks are constrained by provider allowlisting, state validation, body/URL limits and idempotent verification. Other routes currently have bounded bodies and result sizes but no global per-IP rate limiter; deploy an ingress limit for anonymous routes and monitor 429/latency before adding per-operation application throttles.

Presigned media uploads use the initiation response's exact short-lived form URL/fields and private bucket; the browser sends the file directly to MinIO, then calls completion. The service verifies decoded content and metadata rather than trusting extension/MIME claims. Never put a signed URL in telemetry or share it across users. See [media storage](media-storage.md).

Admin realtime clients connect to `/ws?role=admin` with same-origin admin cookie and `printing.read`; the fixed room is read-only and status API is authoritative after reconnect. A café print bridge connects to `/ws?role=bridge`, registers protocol v1 with printer ID/token/instance ID, heartbeats, receives `print.job`, and sends matching ACK only after adapter acceptance. See [realtime printing](printing-realtime.md) and [local bridge](local-print-bridge.md). Realtime credentials never appear in a URL.

Server Components call composed application services directly after the server-side page guard. They must not HTTP-fetch this same app's `/api` routes. The HTTP layer exists for browser clients, provider callbacks, health probes, and other external consumers; it is not an internal service bus. Existing browser Client Components currently use only the admin login/logout endpoints. Query DTOs are constructed explicitly, and Mongoose documents stay behind server-only module boundaries.
