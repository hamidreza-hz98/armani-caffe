# Payment gateway settings dashboard

`/dashboard/settings/payment` is OWNER-only. It uses the existing encrypted, revision-checked Payment settings singleton. The page and `GET /api/admin/payment/settings` return only settings values, adapter registration metadata and **whether** a provider credential exists. Neither returns a stored credential, including after a write. Secret input is blank on every edit; blank means unchanged. A submitted replacement stays on the server and is merged with other encrypted provider credentials rather than overwriting them. The form supports an explicit encryption-key rotation flag.

Only `gatewayFactories` registered in `src/server/commerce/payment-adapters.ts` can be configured or selected. At present that registry is empty: the `fake` adapter is available only outside production for deterministic development, and `iranian-gateway` is a disabled placeholder, not a bank integration. No named Iranian bank, undocumented endpoint, synthetic uptime percentage, or automatic failover is implied. The UI can render up to four installed adapters when implemented. Priority buttons update contiguous `priority` values. Disabling the default clears `defaultProvider`; the server validates the same invariant.

The callback address is generated from `PAYMENT_CALLBACK_BASE_URL`; the `{id}` segment is the server-issued payment identifier, not an operator-entered value. Technical identifiers and URLs use LTR isolation. `POST /api/admin/payment/probe` is owner-only and same-origin. In development it self-checks the local fake adapter and explicitly labels the result a simulation. A real adapter without a separately documented, non-charging credential probe reports **unavailable**, never a fabricated success. Installing a real adapter must include its official API contract, credentials schema, callback behavior, and safe probe implementation.

`PATCH /api/admin/payment/settings` requires an idempotency key, expected revision, complete typed values, and optionally one provider credential replacement/clear operation. The server enforces installed IDs and rechecks the owner role and Origin. A lost response can be retried with the same key. Uncommitted form changes warn before navigation. The separate `/api/settings/payment` contract remains available to other authorized settings clients and also enforces installed adapter IDs.

Run `npm run test:e2e:payment-settings` for production-like owner/cashier and redaction checks. Unit tests cover priority ordering, default disabling, and server allowlisting; settings integration tests cover encrypted persistence/rotation. The supplied Stitch screen is visual direction only—its sample bank names and health numbers are not live data.
