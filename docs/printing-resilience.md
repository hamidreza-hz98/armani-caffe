# Invoice printing resilience and acceptance

Run `npm run test:printing:resilience` for the isolated MongoDB replica-set suite. It verifies paid checkout, order/invoice/outbox creation, duplicate event suppression, queue scheduling, WebSocket delivery, bridge adapter acceptance, matching ACK, and an audited reprint against the same invoice. It also injects the failures below. The suite uses a fault-controlled Redis schedule boundary so it can run without altering a shared Redis instance. Run `npm run test:printing:redis` separately against a dedicated test Redis to verify the real adapter and persistence across adapter reconnect; set `REDIS_TEST_URL` if it is not local. Do not stop or restart a Redis service carrying live orders as a test.

| Injected failure                                       | Recoverable state and operator action                                                                                                                                       | Automated evidence                                              |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Payment callback replay / duplicate invoice event      | One order, immutable invoice, and automatic PrintJob; idempotent outbox replay does not create another job.                                                                 | `orders.test.ts`, `printing.test.ts`                            |
| Worker or Redis-schedule interruption after job insert | Mongo job remains `queued`; restarted dispatcher reconciles Mongo into the schedule. Check realtime `/ready` and restart the worker after Redis is healthy.                 | `printing.test.ts` Redis interruption and process-restart cases |
| Socket disconnect or lost ACK after adapter acceptance | Server stays `printing` until lease expiry, then `queued` with `ACK_TIMEOUT`; bridge journal says `printed` and re-ACKs the redelivery without another adapter call.        | `printing.test.ts` slow-printer/socket-loss/bridge-restart case |
| Duplicate delivery or two bridge instances             | Matching ACK is idempotent; the journal suppresses a second adapter call and printer presence admits only one live bridge.                                                  | `printing.test.ts`, `bridge.test.ts`                            |
| Slow printer                                           | Job remains `printing` while the adapter is pending; no ACK is sent before adapter acceptance. Keep the bridge/journal running and inspect the device if the lease expires. | `printing.test.ts` slow-printer case                            |
| Definite printer error                                 | Error ACK moves job to retrying `queued`, with bounded backoff and visible failure code; fifth failure is `dead`. Repair the printer before an audited reprint.             | `printing.test.ts` printer-error case                           |
| Malformed delivery                                     | Bridge rejects it before adapter output; server lease expiry queues a retry. Correct the payload/protocol mismatch before redelivery.                                       | `printing.test.ts` malformed-job case                           |
| Bridge restart after accepted output                   | Persistent journal survives restart; redelivered job is ACKed, not physically printed again.                                                                                | `printing.test.ts` restart case, `bridge.test.ts`               |
| Manual reprint                                         | New audited PrintJob and journal ID point to the original immutable invoice; the existing job remains unchanged.                                                            | `orders.test.ts`, `printing.test.ts`                            |

The dashboard order detail and `GET /api/admin/orders/{id}/print` display `queued`, retrying (`queued` after an attempt), `printing`, `printed`, and `dead` jobs. Refresh the status after reconnect because WebSocket status hints are not authoritative. A `dead` job is not automatically replayed: diagnose the failure, inspect whether paper actually emerged, then use the confirmed/audited invoice reprint action if a new physical copy is required. Never delete journal entries or reset Redis to force a print.

There is an unavoidable ambiguity between the printer accepting bytes and the bridge persisting `printed`. A journal entry left at `received` is **not** auto-retried. Stop the bridge, inspect the paper and spooler, then use `npm run bridge:resolve -- JOB_ID printed --confirm` if it printed, or `npm run bridge:resolve -- JOB_ID retry --confirm` only if it did not. Restart the bridge and wait for server redelivery. Network and Windows spool adapters report transport/spool acceptance, not verified paper output; no generic protocol can promise exactly-once physical printing.

## Manual acceptance checklist for the actual café printer

Record the printer model, firmware, connection type, driver, paper width, and test date. Use a dedicated test order/invoice, never a customer's live payment. Keep file-simulator output and the actual printed slip for comparison.

1. Set the intended 58 mm or 80 mm width and confirm a Persian receipt with mixed Latin reference/phone digits, long names, additions, totals, footer, and correct RTL shaping. Check clipping, feed length, cutter, and legibility.
2. Print one automatic receipt and verify one physical copy, one `printed` server job, one `acknowledged` bridge journal entry, and matching invoice/order/job IDs. A successful socket send alone must leave the job unprinted.
3. With a test job, unplug the printer **before** output and verify a visible retry/error; restore it and confirm a single eventual copy. Repeat a network/spool interruption **during** output and verify the bridge holds `received` for manual reconciliation instead of silently printing a second copy.
4. Disconnect the bridge network after the printer accepts a test slip but before ACK; reconnect/restart the bridge and verify the original job does not produce a second slip and eventually becomes `printed` on the server.
5. Restart the realtime worker and Redis one at a time only in a maintenance/test environment. Confirm queued jobs recover from MongoDB and the dashboard status catches up. Never perform this on a live queue merely to run a test.
6. Trigger an explicitly confirmed reprint and verify it uses the same invoice snapshot but a **new** job ID, creates an audit record, and produces exactly one additional physical copy.
7. Sign off the observed results and any printer-specific limitations before enabling unattended automatic printing. If the device cannot report paper emergence, document that transport/spool acceptance is the strongest available guarantee.
