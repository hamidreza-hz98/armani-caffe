# Operational orders dashboard

The responsive `/dashboard/orders` page is server-rendered from a bounded DTO query (20 rows/page) and enhanced by a read-only realtime client. Both OWNER and CASHIER have `orders.read` and `orders.manage`. The existing order service remains authoritative for every transition. Bulk advancement sends individual version-checked transitions, then re-fetches; it may partially succeed, and the UI reports failures rather than promising an atomic batch. Cancellation and refunds remain their separate owner-only workflows.

Fulfillment (`NEW`, `PREPARING`, `READY`, `COMPLETED`, `CANCELLED`) and payment (`unpaid`, `pending`, `paid`, `refunded`) are never merged into one status. Date filters use Asia/Tehran day boundaries against UTC `placedAt`. Searches accept an order-code prefix or exact normalized Iranian mobile; no arbitrary regex is accepted. Sort/page/count queries are bounded by `maxTimeMS=2500`. Apply `order_customer_phone_placed` and `order_amount_sort` indexes intentionally using `npm run db:indexes:plan` and `npm run db:indexes:apply -- --apply`; normal requests do not synchronize indexes.

Start the realtime process with `npm run realtime:work` alongside the web app and infrastructure. The worker consumes order outbox events and broadcasts identity-only hints to `/ws?role=orders`; no customer data is pushed. Auth is checked on connect and heartbeat. The page re-fetches from MongoDB after a notice, on socket open/reconnect, on tab return, and every 30 seconds. A socket drop shows an offline indicator but does not block HTTP-backed actions; a failed re-fetch marks the list stale and disables transitions. Realtime is deliberately not a durable event cursor: missed events are recovered from the authoritative list. Browser-local saved filters contain only status/payment/range/sort (never customer search text), and audio is off until explicitly enabled after a browser gesture.
