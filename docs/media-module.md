# Media application module

## Responsibilities and permissions

The Media application service validates inputs, initiates uploads, completes/recovers them, edits metadata, searches/lists records, resolves product usages, replaces referenced assets, and schedules safe deletion. The injected `MediaRepository` and `MediaStorage` ports isolate database and object-store details. Only plain DTOs leave the module; no Mongoose documents, private object paths, encrypted tickets, or signed upload tokens appear in public metadata/list responses.

`OWNER` means the café administrator role, not merely the uploading account. Any verified OWNER can manage the café's library; uploader and storage-owner IDs remain attributable. CASHIER and anonymous users can read only explicitly public, ready images. New media is private unless the OWNER deliberately submits public visibility. File routes proxy bounded bytes from the private bucket rather than revealing paths or requiring a public bucket/CDN. Metadata and file responses are `no-store`; file responses include an ETag and validate access before a 304 response.

Task 14 connected `handleMediaHttp` to the verified active admin session resolver. Mutations/usages require a valid owner session; public reads remain available. `createMediaHttpHandler` and `createMediaActions` accept a trusted server-side authenticator; never derive actors from JSON, custom role/ID headers, or unsigned cookies. Application permission tests use injected trusted actors. Thin future `use server` wrappers should call `createMediaActions`; Server Components can call the application service directly.

## Data and workflow

Each `media_assets` record persists original display filename, object key/version, normalized MIME/size/dimensions/hash, all image variants, title/alt/caption, bounded SEO title/description/keywords, visibility, uploader/storage owner, UTC timestamps, optimistic metadata revision, upload fingerprint/idempotency key, expiry and completion lease. Signed ticket capabilities are AES-256-GCM encrypted at rest with purpose-bound AAD. Rotation reads the explicitly configured previous key as well as the current one. No ticket is read from an untrusted completion callback.

Initiation validates metadata and image claims, then stores a durable intent before returning a signed POST policy. Repeated requests with the same uploader/key and normalized payload return the same asset ID and staging key. Policies can be refreshed for that staging key during the fixed 15-minute intent window; capability URLs need not be byte-identical. A different payload under the same key conflicts. Single upload keys are 8–128 ASCII letters/digits/underscore/hyphen. Bulk requests derive deterministic per-item keys from the full key hash and index, avoiding truncation collisions.

Completion uses a five-minute database lease and a fixed server-generated output UUID. It first looks for an already normalized complete version; otherwise it removes partial outputs and normalizes the private staging file. The stable output intent permits recovery after object writes but before database persistence. Staging is retained until the ready record and a cleanup job commit together. Duplicate callbacks for a ready asset return the same current DTO without re-encoding; a simultaneous active callback receives 409 and can retry. Invalid content is rejected and scheduled for cleanup; transient failures release the lease for retry. All three descriptors must have correct owner/version/hash keys, distinct variants, WebP type, positive bounded size/dimensions.

Metadata editing replaces the full metadata contract and requires an expected `revision`. Update/delete/replace use durable mutation receipts: identical key/payload retries replay the response; reused keys with different payloads conflict. Receipts are retained rather than expiring keys silently. Metadata deletion tombstones an unreferenced asset and atomically enqueues object cleanup. Public referenced media cannot be made private without a deliberate reference-resolving workflow. Replacement requires two ready assets and preserves public access, rewrites source references, tombstones the old asset, and enqueues its cleanup in one transaction.

## References and concurrency

Products are currently the only modeled documents with an explicit `mediaIds` field. Media references are indexed in `media_references`; an owning Product-module adapter also checks source records, including pre-registry/archived links. Thus a missing registry entry cannot silently permit deletion of an existing product image. Media infrastructure never imports another module's schemas/repositories; the bridge is composed through the Product server public boundary.

Product services must write `mediaIds` through `withProductMediaReferences`: it locks old/new media records, verifies readiness, runs the product write in the same transaction, checks that the actual source matches declared IDs, and synchronizes the registry. No external side effects belong in that callback because transaction retries can execute it again. Reference attachment and deletion touch the same media guard, so only one side of a conflicting race can commit. Replacement updates actual product arrays and the registry atomically; failed rewrites roll back. Do not write media reference fields directly through MongoDB or bypass these owning-module services.

Before Task 13 or another module introduces a media-bearing setting/category/etc. field, extend the usage contract/schema and owning-module bridge, and add transactional synchronization plus replacement tests. No unsupported reference kind is accepted by the current API, and clients cannot create arbitrary references via HTTP. Historical snapshot references must be retained, not detached merely to delete an image.

## HTTP and action contracts

JSON responses are `{ ok: true, value }` or `{ ok: false, error: { code, message, requestId } }`; errors use safe Persian messages and correlated operator logs. Mutation requests require an authenticated OWNER, an `Origin` matching configured APP_URL/ADMIN_URL origins, JSON if a body is present, and an actual streamed body size ≤64 KiB. Image bytes go directly through the signed policy, not these JSON routes. Signed fields are bearer capabilities and must never be logged.

| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/media`                        | Public ready list, or OWNER library after authentication wiring. `page`, `pageSize` (1–100), `sort` (createdAt/updatedAt/title/byteSize), `direction`, `q` (≤80 chars), `mimeType`, `visibility`, `status`, `uploaderId`. Offset ≤10,000. Public queries cannot override visibility/status/uploader guards. |
| `POST /api/media`                       | Idempotency-Key header; `{ filename, mimeType, byteSize, metadata }` → `{ id, status, upload: { url, fields, expiresIn } \| null }`. Copy fields to multipart/form-data and append the file last.                                                                                                           |

ID itself is the completion idempotency identity.                                                                                                                                                                                          |

`metadata` is `{ title, altText, caption, visibility: "private"|"public", seo: { title, description, keywords } }`. All fields are bounded plain text, with no HTML/control characters, arbitrary URLs, unknown keys, or user-supplied object paths. Filenames are display metadata only, not content detection or object naming.

## Indexes, migration and recovery

List queries project summary fields only and use lean records. Named indexes cover status/visibility plus each sort, MIME browsing, uploader/date, text search (language `none` for Persian), initiation uniqueness and pending expiry. Source product media IDs, usage lookup, mutation receipts and cleanup claims have dedicated indexes. Counts and list queries have bounded Mongo execution times. No auto-index or migration happens during requests.

On an existing database run `npm run db:migrate:status`, then explicitly `npm run db:migrate:up -- --apply` before `npm run db:indexes:apply -- --apply`. Migration 0002 quarantines pre-workflow media as private/rejected with `legacyReviewRequired`; it preserves original object keys and does not delete or invent file metadata. Operators must inspect/revalidate/re-import these records deliberately. Legacy records cannot be deleted/replaced through this module until that review is resolved. New pending records use a distinct staging key in the existing unique object-key index, so its definition does not need an implicit destructive index replacement.

Run `npm run media:cleanup -- --apply` as a scheduled operator/worker command. It quarantines expired idle upload intents, claims bounded cleanup jobs, removes known output-version prefixes and staging keys, and retries storage failures with capped backoff. Claims are token-guarded; completed jobs expire after 30 days, while failed jobs remain pending for recovery. The command reports JSON counts and exits nonzero if a cleanup or shutdown fails. The janitor is not called as a side effect of public reads. Monitor pending job age and failed command results; a scheduled process is necessary in deployment. The bucket's one-day staging and incomplete-multipart lifecycle remains a fallback.

Object-store effects are not MongoDB-transactional. Completion/cleanup may run again after a lease loss or process pause; object versions and durable intents make them recoverable, not exactly-once S3 writes. Do not run unbounded custom storage implementations beyond the lease deadlines. Review unreferenced upload-version intents before manual cleanup, and never scan/delete arbitrary user-supplied prefixes.
